# Domain Knowledge: Internal Products

> REFERENCE, not a skill. Skills read this when the product is built for employees
> / internal teams (tools, platforms, dashboards, workflow systems). The economics
> are NOT revenue — they're efficiency, risk-reduction, and enablement. Applying a
> B2B or B2C revenue model here produces nonsense.

---

## The defining truth of internal products
**There is no revenue. Value = cost avoided + time saved + risk reduced +
capability enabled.** The "customer" is a colleague; the "market" is captive but
not compliant — mandated tools still fail if they're bad, because people route
around them (shadow spreadsheets, workarounds). Adoption is the whole game.

## How "money" works (value, not revenue)
- **Time saved** → hours × loaded cost × # users × frequency = $ value.
- **Cost avoided** → headcount not hired, errors not made, tools not bought.
- **Risk reduced** → compliance, security, fewer incidents (harder to quantify,
  real value).
- **Capability enabled** → makes something possible that wasn't (decision speed,
  new workflow). Strategic, hardest to put a number on.

## Core metrics (use THESE for internal, not ACV or DAU-for-monetization)
| Metric | What it is | Why it matters |
|--------|-----------|----------------|
| **Adoption %** | Of eligible users actually using it | The #1 metric — no adoption, no value |
| **Active usage** | DAU/WAU among the target team | Is it in the workflow or ignored? |
| **Time saved / task** | Before vs. after | Primary value driver |
| **Task completion / cycle time** | Speed of the workflow | Efficiency proof |
| **Error / rework rate** | Mistakes before vs. after | Quality + cost avoided |
| **Cost avoided** | $ not spent | Headcount, tools, rework |
| **Satisfaction (internal NPS/CSAT)** | Do employees like it? | Predicts sustained adoption |
| **Shadow-tool usage** | Are people routing around it? | Failure signal even if "mandated" |
| **Support/ticket load** | Cost to run it | Ongoing drag on value |

## The adoption reality
- **Mandated ≠ adopted.** People use the worst-but-required tool minimally and
  keep their real work in spreadsheets. Measure *actual* usage, not licenses.
- Voluntary adoption is the honest signal: if they'd choose it, it's good.
- Change management is part of the product: rollout, training, champions matter
  as much as features.

## What "good" looks like
- High adoption among eligible users, with **low shadow-tool usage**.
- Measurable time saved / errors reduced, defensible in $.
- Internal satisfaction high enough that people would keep it voluntarily.

## Business-case levers (what to model)
- (Hours saved/user × # users × frequency × loaded hourly cost) − build/run cost.
- Cost avoided (headcount, external tools, incident cost).
- Risk/compliance value (qualitative + any quantifiable exposure reduced).
- Adoption assumption is the biggest risk in the model — flag it, plan for it.

## Common traps the agent should flag
- Assuming "mandated" means "adopted" — model real adoption, not licenses.
- Ignoring change-management cost (training, rollout) in the case.
- Over-precise $ on soft benefits (decision speed) — mark as qualitative.
- Building for the sponsor (exec who asked) not the user (who must adopt).

## "GTM" shape (internal rollout)
- Pilot with one team → prove value → champion-led expansion → org rollout.
- Training, docs, and a feedback loop are the "marketing." Adoption is the "sale."
